## Phase 2 — Spec path (weeks 3–4)

- [x] **T2.1** `api/services/spec_query.py` — structured lookup, pure SQL, no LLM. Returns facts with sources attached. Test that the response type cannot represent an uncited fact.
  - `CitedSpec`/`CitedFeature`/`CitedSafetyRating` require a non-optional `source: SourceRef`, so an uncited fact is a Pydantic `ValidationError` at construction, not a runtime check. Query functions: `get_specs_for_variant`, `get_features_for_variant`, `get_safety_ratings_for_model`, `find_variants_with_feature` (feature + price cap, e.g. "panoramic roof under ₹70 lakh"), `find_variants`.
- [x] **T2.2** `api/services/router.py` — classify query as SPEC, COMPARISON, or OBJECTION. Target under 100ms. Test on 50 labelled queries.
  - Rule-based (regex/keyword), not a model: `llm/client.py` doesn't exist yet (T4.1), and a plain regex pass is well under the 100ms budget without adding an LLM call to a path that doesn't strictly need one. Precedence: OBJECTION markers checked first (an objection can contain comparison or spec-shaped wording), then COMPARISON (vs/compare wording, or 2+ brand/model mentions), else SPEC. All 50 labelled queries in `test_router.py` pass; revisit with a real classifier if the heuristic's false-negative rate on live queries turns out too high.
- [x] **T2.3** `/spec` and `/compare` endpoints. Compare returns a structured diff with sources per row.
  - `GET /spec?variant_id=&attribute=` wraps `spec_query.py` directly (specs + features, 404 if both empty). `GET /compare?variant_a_id=&variant_b_id=` uses new `api/services/compare.py`: unions both variants' spec attributes, one `SpecDiffRow` per attribute with `variant_a`/`variant_b` each `None` or a cited `DiffValue` — an attribute present on only one side still gets a row rather than being dropped, since the absence is itself something a consultant needs to see. Tests use an in-memory SQLite engine with `StaticPool`/`check_same_thread=False`, required because `TestClient` runs requests on a separate thread from the fixture that built the session.
- [x] **T2.4** Equipped-price comparison — sum `availability='optional'` costs on the competitor to produce a like-for-like figure against Volvo's standard kit. This is the core value proposition; get it right.
  - `equipped_price_comparison` in `api/services/compare.py`, exposed as `GET /compare/equipped-price?base_variant_id=&competitor_variant_id=`. For every feature standard on the base (Volvo) variant: standard on the competitor too → no added cost; optional with a sourced `cost_paise` → added to the total and reported as a cited `IncludedItem`; unavailable, or optional with no sourced cost → reported as an `UnmatchableItem` (`not_offered` / `cost_not_sourced`) rather than silently dropped, since omitting an unpriceable gap would understate the very gap the feature exists to show. `competitor_equipped_price_paise` is `None` when either variant's base price is unsourced (per T1.4, `ex_showroom_paise` is nullable) — never coerced to 0.
- [x] **T2.5** Battle card generation, offline, for the main Volvo-versus-German pairs. Store in `battle_cards` with `stale_after`.
  - `api/services/battle_card.py`: `generate_battle_cards(db)` runs `compare_variants`/`equipped_price_comparison` once per pair and freezes the result as `content_json`, upserting by `(variant_a, variant_b)` so reruns update in place rather than duplicating. Pairs come from a curated `MODEL_PAIRS` list (`XC60`×`X3`/`GLC`/`Q5`), not inferred from `body_type` — a first attempt at body-type matching also paired EX30 (compact EV) with X3 (mid-size ICE) since both are `body_type='suv'`, which is exactly the wrong comparison; caught by a test and fixed by switching to an explicit list. `stale_after` defaults to 30 days (no corpus-mandated figure; matches the general re-verify cadence, revisit if facts churn faster). Runnable standalone via `python -m api.services.battle_card`. Not yet wired into `/compare` as a read-time cache — that's the "lookup + fallback" behavior ARCHITECTURE.md describes for `compare.py`, left for when latency work (T6.2) needs it rather than built speculatively now.

## Phase 4 — Objection handling (weeks 6–7)

- [x] **T4.1** `llm/client.py` — provider-agnostic wrapper. Retries, timeouts, token and cost logging. The only file importing a vendor SDK.
  - `api/llm/client.py` is the sole importer of the `anthropic` SDK (new dependency, added to `pyproject.toml`); everything else sees only `LLMClient.complete()` plus `Message`/`CompletionResult`/`LLMError`. Retries: up to `max_attempts` with exponential backoff, only on transient errors (`RateLimitError`, `OverloadedError`, `InternalServerError`, `APIConnectionError`, `APITimeoutError`) — a bad request or bad API key raises `LLMError` immediately, since retrying can't fix either. Timeouts are passed through per-call to the SDK. Every call logs model, input/output tokens, latency, and an estimated cost via `structlog` (AGENTS.md's logging rule) and returns the same fields on `CompletionResult`. Cost is computed from a hand-maintained `PRICING_USD_PER_MTOK` table — documented as this module's own estimate (Anthropic's API reports tokens, not dollars), `None` and a warning for any unlisted model rather than a guessed number. The underlying client is injectable via a structural `_AnthropicLike` Protocol so `api/llm/test_client.py` (11 tests) can test retry/backoff/logging behavior with a fake that scripts a sequence of responses/errors, with no real API key or network call needed. Full suite: 151/151 passing, ruff/mypy clean.

- [x] **T4.2c** Reranking — cross-encoder, top-50 → top-5. Measure precision gain and latency cost per track; decide and document.

- [x] **T6.4** Optimise until p95 is under 2s on the objection path. Document what worked and what didn't — the failed attempts are interview material too.
  - **Honest framing first, since it shapes everything else here**: no `ANTHROPIC_API_KEY` exists in this sandbox, so the actual dominant cost on this path — real Claude inference time — has never been measurable here, and T6.1's baseline (objection p95 ≈ 18ms) times a scripted, zero-latency LLM proxy exercising real control flow, real SQL, and real (empty) hybrid search only. "p95 under 2s" can't be honestly claimed or falsified against real generation without a live key. What *is* addressable and real regardless of a key: how many sequential LLM round-trips a single objection turn makes, since each one is pure added latency on the critical path no matter how fast any individual call is.
  - **What worked**: every objection turn was making 3 sequential LLM calls per generation attempt — classify, generate, and (T4.4) a separate structured `extract_claims` call inside `verify_grounding` just to split the generated text into checkable claims before grounding-matching them. That claim-extraction call added an entire network round-trip to a node that runs on *every* attempt including the retry, for a job — splitting text into claims — that doesn't need a model at all. `api/objection/verify.py::extract_claims_deterministic` replaces it with a plain sentence split, the same sentence-level granularity `evals/ragas_metrics.py`'s `faithfulness` proxy already uses for the identical reason (T4.6). This cuts a full generation attempt from 3 sequential LLM calls to 2 — a 33% reduction in the number of round-trips on the path, and removes an entire failure mode with it (`extract_claims`'s LLM-error/unparseable-response cases, and the `claim_extraction_failed` violation they produced, no longer exist — a deterministic function can't fail the way a network call can). `verify_grounding`'s signature dropped its now-unused `llm` parameter; `generate.py` gained two small public exports (`parse_generated_response`, `build_generate_prompt`) so T6.3's streaming path and this change share the exact same prompt/parsing logic rather than duplicating it.
  - **What didn't (a real, accepted trade-off, not hidden)**: sentence-level claim extraction is coarser than what an LLM extractor could do — a single compound sentence covering one grounded fact and one fabricated one is now judged as one claim rather than two, so a specific class of mixed-truth sentence could pass grounding it shouldn't. Accepted because removing a full sequential network call from every generation attempt (and every retry) was judged the larger, more certain win, and because the existing lexical-overlap grounding check (T4.4) already carries a comparable, already-documented imprecision one layer down.
  - **What wasn't attempted, and why**: parallelizing `retrieve_facts` (SQL) and `retrieve_chunks` (embedding call) within the same node was considered, since they're independent given the classified category — but both take the same SQLAlchemy `Session`, which is not safe to use concurrently from two threads, and giving each its own session/connection is a bigger change than this task's scope justified for a step T6.1 already measured at sub-millisecond overhead against the real corpus. Not pursued; noted here so a future latency pass doesn't have to rediscover the same dead end.
  - Updated every call site of `verify_grounding` (`graph.py`, `stream.py`) and every test that scripted a now-nonexistent claim-extraction LLM reply (`test_verify.py`, `test_graph.py`, `test_stream.py`, `test_objection.py`, `evals/run_eval.py`'s `_ScriptedObjectionLLM`) to the new 2-call shape. Net new/changed tests: `test_verify.py` replaced 4 LLM-mocked `extract_claims` tests with 3 tests of the deterministic version plus one extra `verify_grounding` pass-case test.
